## 未发布 — 专家目录：接入 331 位专家（MichengAI/dsh-agency-agents）

专家库不再只有我们手写的那 14 张。它现在挂着一条**货架**：331 位按 22 个领域分好类的专家，点了才进你的库。

**新增**
- **专家目录（331 位）**：来自 [MichengAI/dsh-agency-agents](https://github.com/MichengAI/dsh-agency-agents) 的中文专家库，覆盖技术工程 / 设计 / 市场营销 / 销售 / 游戏 / 金融 / 医疗 / 法务 / 学术等 22 个领域，逐位生成 App 的人设卡格式（称呼 / 关系 / 语气 / 主题 / 情境 / 三条规矩 / 两三句示例）。
- **目录分类抽屉**：分类从 5 个扩到 25 个（老的 5 个仍在最前），每个抽屉里都是真有条目的。
- **一条卡两种身份**：目录条目点「用这个专家」会先落进你的库再套用（热度得有地方记）；点「加入我的专家库」只入库不改当前人设。入库后就是普通专家：能改名、能改正文、能删、能导出。
- **不重复**：已经入库的那位，同 `presetKey` 的目录样品不再单独列一份；你改过的名字和正文不会被目录覆盖。

**改进**
- 预设 → 人设条目的映射收敛成**一条路径**（`PersonaPreset.asProfile`），内置预设和目录共用；此前只有内置预设能派生条目。
- `tools/gen_experts.py`：上游更新后一条命令重生成目录，`--check` 校验生成物与上游一致（防止手改 JSON）。

**验证**

**已知限制**
- 目录只读：不能批量「全装」（331 条一次性写进人设库会让库变得没法翻）。
- 目录正文是**提炼卡**（约 250 字），不是上游 2–8KB 的完整操作手册；完整手册不进提示词。

## 未发布 — 回复自然度 P0：先判后写、关系优先级、n 感知策略契约、避谈键

用户反馈：「生成出来的语句很诡异、非常不自然」。用生产提示词导出通道（`RoleplayFixtureTest` 回放）逐字核对后定位到四个「模型看到的事实就错了」的根因——不是文风问题，是提示词把模型放进了几个互相打架的场景。完整诊断（含外部同类项目调研）见 `_reports/reply-naturalness-p0_report.md`。

**修复**
- **首轮起草不再盲写（先判后写）**：判断和起草过去是并行的，`draftOnly` 根本没有 judgment 参数，`JevClient.draftStream` 还硬编码 `judgment = null`——判断结果只用来排序，写的时候模型不知道这一场是吵架、玩笑还是角色扮演，轻松闲聊被按想象中的危机写。现在起草等判断：判断回来带着它写；等满 2 秒（`DraftTrigger.WAIT_MS`）还没回来就盲写，判断路由慢或挂掉时延迟有上界。触发语义抽成纯类 `DraftTrigger`（fire 恰好成功一次、判断优先于超时），JVM 单测钉死。「再给 2 条」的追加起草也带上 `lastJudgment`。
- **关系优先级统一（联系人 > 全局）**：全局默认关系从「对方是我的伴侣；from=me 的是我发的…」改成中性的「朋友」——旧默认把每一段销售/同事对话都框成伴侣聊天，还混着给协议层看的 from 说明。新增 `effectiveRelationship`：联系人自己写的关系压过全局，判断、起草、排序、复查、微调五条路全部走同一个值；联系人有关系时提示词里「关系：」只出现一次（过去是背景块一份 + 正文行一份，两行还会打架）。
- **候选条数 n=2 不再自相矛盾**：旧系统提示词在任何 n 下都要求 safe/forward/angle 三种策略「各一个」——只要 2 条候选时算术上不可满足。n=2 现在只点名两条策略。
- **收着档不再强迫推进**：判断说「局势偏紧、该收着」的轮次，系统提示词仍强迫一条「forward（推进话题）」，和档位块的「不要邀约、不要加码」同场打架。收着轮把 forward 重定义为温和确认（标签不变，下游解析/排序/卡片不动）；system 契约和 user 档位块改用同一个 `Intensity.resolve` 解析结果。自然档 n=3 的契约逐字不变（默认轮次提示词与之前逐字节一致的兼容锁继续通过）。
- **「硬边界」的两种语义拆开（新增「避谈」键）**：`SafetyGate` 把硬边界当「对方一提就拦整轮」，提示词又把它当「我的回复不许出现」——日常卡的「工作、家人」让朋友说句「最近工作好累」就没候选，销售卡的「稳赚、保证收益」在客户问「能稳赚吗」时恰好掐掉最需要回的一轮。新增人设卡键 `避谈`（只约束我方措辞，对方提到照常回）；日常卡删掉误拦词，销售卡改用避谈；网调卡的家人/前任仍是硬边界（那才是「对方一提就该停」）。
- **低置信度判断不再当事实念**：判断意图的 confidence < 0.5 时，判断块降级成「把握不大，按字面承接」，不再给「局势轻松/偏紧」之类的场景定性。chat 协议解析对缺失 confidence 填 0.0，按「没说」处理而不是「很低」，避免省略字段的模型每轮都被降级。
- **起草温度回归用户设置**：删掉「avoid 非空就 +0.1」——跨轮 avoid 现在几乎每轮非空，等于全局偷偷调参；反重复交给 avoid 文本与复查第 6 条。

**改进**
- 设置页关系描述的说明改为「判断与起草都用；联系人里写了自己的关系时以它为准」；人设键列表、新建骨架、联系人人设提示都补上「避谈」及两种边界的区别。
- `PersonaStatus` 的识别回显与库列表摘要带上「避谈 N 词」。

**验证**
- 单测 603 → 615（+12：`ReplyPromptTest` 6 例、`DraftTriggerTest` 3 例、`PersonaCardTest` 1 例、`PersonaPresetsTest` 1 例、`IntensityTest` 1 例），0 失败；`assembleDebug` 通过。
- 生产提示词导出复核：默认轮（判断 casual_chat 1/9 + 全局关系）的 user 提示词里判断块在场、`关系：` 恰好一次；自然档 n=3 策略契约逐字未变。
- 真机（PJE110，覆盖安装）：新包安装成功、无障碍自动重绑；设置页「测试判断」走 DeepSeek chat 协议跑通（成功 1615ms · 意图=casual_chat 置信 70%）。用户接管继续自测。

**已知限制**
- 服务层「先判后写」的编排跑在 Android Handler 上，JVM 测不到——`DraftTrigger` 钉住的是触发语义；真机上「判断先回 → Trace `draft start judged=true`」这条还没看到，自测时留意 Trace。
- 常见路径延迟会涨约一个判断耗时（Jev 实测约 900ms；chat 协议判断更慢，最多多等 2 秒）。
- 旧安装里存过旧默认关系的用户不受影响（存的是明文，只有从未设置过的安装才拿到新默认「朋友」）。
- 自然度本体（文风、句长、AI 腔）属于 P1/P2：自动「我的说话方式」画像、提示词减重与重排、正向示例化改写、日常场景评测集，见报告的后续清单。

## 未发布 — 人设库：人设从「写死三张」变成用户可以自己攒

用户要求：「人设应该是一个用户可以自己配置的功能，不是硬编码的 —— 比如我销售的时候需要一个销售的说话风格」。

原来的结构确实是写死的：`PersonaPresets.ALL` 里三张卡（网调·主 / 网调·奴 / 日常），设置页三个按钮一键填进一个文本框，填完就只剩那段文本。卖货的话术、客服的口气、和甲方说话的分寸，每次都要重敲一遍，关掉页面就没了。

**新增**
- **人设库**（`filesDir/kb/personas.json`，`PersonaStore`）：新建 / 改名 / 复制 / 删除 / 恢复内置模板 / 导入 / 导出（JSON 走剪贴板，不申请存储权限）。首装播种四张种子；逐条删光**不会**再长回来。
- **第四张内置卡「销售·跟单」**：主题「销售」+ 称呼按对方名片 + 硬边界「稳赚」「保证收益」（不能承诺收益）。用户提的那个场景，开箱就有一份能改的样例。
- **设置页人设区重做**：库列表（每行带「生效中」标记和一行摘要）+「用 / 改 / ⋯」+ 新建/导入/导出/恢复模板，下面才是人设原文。新建时预填键骨架，正文旁实时回显「认出了什么」——认不出键是静默的，界面必须当场说出来。
- **「收进语气示例」**：把知识库里标了语气示例的笔记抄成「我：…」进卡片的示例段，换机器不丢。
- **联系人专用人设也从库里一键套**（原来用的是同一批写死的模板）。

**改进**
- 「清空知识库与历史」的确认文案带上人设条数，并说明人设会回到内置模板。

**设计取舍（写下来免得以后被改回去）**
- **「当前生效是哪一条」不存 id**：生效的仍然是 `Prefs.style` 那段文本，界面靠原文比对反推。多存一个 id 就多一处能漂移的状态，而漂移的表现是「界面说生效的是 A，发出去的是 B」——这种错没有报错可查。
- **导入永不覆盖同名**：同名不同文另存为 `名字(导入)`；内容完全相同则跳过。
- **文件坏了先备份再放行**（`personas.corrupt-<时间戳>`），不清空用户的库。

**验证**
- 单测 585 → 603（+18：`PersonaStoreTest` 13 例、`PersonaStatusShortTest` 5 例），0 失败；`assembleDebug` 通过。
- 真机（PJE110）走完整条路：套用「销售·跟单」→ `shared_prefs/jev_assistant.xml` 里 `reply_style` 立刻变成销售那张卡；新建 → 保存落进 `personas.json`（`builtin=false`）；⋯ → 删除 → 库回到 4 条、列表重画；最后把生效人设恢复成「网调·我是主」。细节见 `_reports/persona-library_report.md`。

## 未发布 — 手动「生成」：把「换一组点不动」变成一句话或一批候选

用户反馈：在 QQ 等应用里「重新生成」很难触发，想加一个手动生成的选项。

查下来不是按钮难找，是**按钮后面的锁会永久卡住**：`analyzing` 只在「判断和起草都回来」那条路里清，而那条路排在 `if (!isCurrent(token)) return@post` **之后**。QQ 里翻一下列表、输入法弹起、标题抖一帧，结果回来时 `isCurrent` 就是 false，直接 return —— `analyzing` 永远停在 true，之后每一次「换一组」「再给 2 条」「单条重生成」都在第一行被静默挡掉，屏幕上什么都不变。再叠上五处静默 `return`（没快照 / 没 token / token 失效 / 总开关关着 / 上一轮还在跑），用户能得到的唯一结论就是"按钮坏了"。

**新增**
- **手动生成，三个入口**：卡片 header 右侧常驻「↻」、长按菜单「重新生成候选（手动）」、常驻通知「重新生成」。三条路都走同一个 `manualGenerate()`，不依赖任何自动触发条件。
- **手动生成一定给结果**：有快照就直接重起草（有判断只换候选，没判断跑整轮）；没快照但当前应用抓得到就先读一次（节点树优先，其次截屏 OCR），读完自动生成；都不行就把原因显示出来，并指到下一步（「截屏识别一次」/ 打开聊天窗口 / 去设置填密钥）。
- **卡住的一轮可以被手动接管**：忙了超过 8 秒还点，就认为上一轮已经卡死，`cancelInFlight()` 解锁后重来 —— 8 秒内双击只提示「正在生成中…」，不会砍掉正常的一轮。

**修复**
- **`analyzing` / `regenerating` 永久卡死**：所有提前 `return` 的出口补上 `endRound()`，并加一个只看时钟的 `roundWatchdog`（2×请求超时 + 10 秒）兜底；OCR 的 `ocrBusy` 同样加了 30 秒兜底。这两把锁卡住时，所有手动入口一起失效。
- **五处静默 `return` 全部改成可见反馈**：`refineReply` / `moreReplies` / `regenerateReplies` 的前置条件每条都有对应的 toast 或错误行；点卡片 header 而手里没快照时也不再什么都不做。
- **footer 按钮够不着**：`↻` 放在 header 而不是 body 底部——footer 在可滚动区末尾，QQ 里键盘一顶、候选一多就滚出屏幕。

**验证**
- 新增 `ManualGenerateTest`（9 例）锁住判定分支与 8 秒边界。
- 单测 / 构建的真实输出见 `_reports/manual-generate_report.md`。

**已知限制**
- 无快照时的手动生成依赖「截屏识别一次」，仍受 `ScreenCapture` 的 ≥1 秒限频与失败退避约束：连续快速点会被节流，此时给的是限频提示。
- 悬浮窗在系统截图 / 录屏 / uiautomator 里都不可见（系统层排除），`↻` 的观感只能人眼确认；行为证据在 Trace（`manual generate …`、`redraft source=…`、`round watchdog fired`）。

## 未发布 — 上下文与记忆：Telegram 实测反馈的诊断与修复

用户 Telegram 实测反馈「AI 分不清上下文、没有记忆」。trace 实锤（`contact=false notes=7 history=0 skills=0 ledger=none`）：知识库在正常工作，**记忆链路没激活**（会话没存为联系人），写作模型每轮只看最近 10 条。完整诊断与验证见 `_reports/memory-context-verification_report.md`。

**修复**
- **狗头军师几乎永远不命中的真 bug**：单技能安装时 BM25 分数上限 ≈0.57，而命中门槛是 0.6——数学上不可达，技能正文从来没进过提示词。门槛 0.6 → 0.3（特异性把关由「两个不同词都出现」承担）。探针实测：修前同一句冲突场景一个命中一个不命中，修后稳定命中，且自动挑出的参考第一篇就是《万能吵架技巧》。
- **写作上下文窗口 10 → 20 条**：快节奏聊天里十条之前的设定（时间、任务、约定）全部出窗——模型不是"分不清"，是看不见。判断层不动（校准过的载荷）。

**新增**
- **记忆未激活时卡上直说**：会话没存联系人时，卡片第一屏出提醒「长按悬浮卡『把当前会话存为联系人』…」，不再让人猜为什么没记忆。

**验证（真实数据）**
- 拉取真机 679 条真实知识库跑注入探针：网调场景命中 5 条全对题 + 领域卡常驻。
- 实况 A/B（同一 14 条场景，唯一差别有无知识库）：KB 臂回复**引用了第 1 条的时间设定**（"十点整开始"）并主动核验安全词；无 KB 臂只能输出通用模板。知识库真的在起作用。

**已知限制**
- 记忆仍是手动激活（存联系人）：这是隐私设计（聊天内容不落盘需明确授权、联系人绝不自动创建）。要自动建档的话需要用户拍板。

## 未发布 — 不用再点无障碍了：一次性开通之后它自己修

用户报的是：「我的手机是有root的啊……不如我每次打开软件还要点一次那个无障碍，好麻烦啊」。查下来根因不是权限没给，而是**系统说"开着"的时候服务可以完全没在跑**：`am force-stop` 会把 `enabled_accessibility_services` 整格清掉（5 秒后仍不恢复）；`adb install -r` 会保留那一格、只把绑定丢掉（`Bound services:{}`）。修法就是把用户在系统设置里手点的那两下（关掉→打开）自动化，并且**把判据换成"服务真的连上来了"**，而不是"设置里写着开着"。真机原文见 `_reports/root-auto_report.md`。

**新增**
- 主页多一块「root 增强（可选）」：上次修复的**逐行原文**（每行都是真机命令的真实结果，不是概括）、一个「一键修复」按钮、一个「自动修复」开关。默认关 —— 与项目「不 hook、root 只是可选增强、不开也完全可用」一致。
- 「一键修复」修四件事：无障碍、悬浮窗、写系统设置权限、省电白名单。每件都走能力阶梯：有 `WRITE_SECURE_SETTINGS` 就直接改系统设置（**不 spawn su**），没有才 `su -c settings put`，两条都走不通就如实说"只能手动"。
- 「自动修复」打开后：打开软件时、覆盖安装后自动修（`MY_PACKAGE_REPLACED` / `BOOT_COMPLETED` / `LOCKED_BOOT_COMPLETED` / `QUICKBOOT_POWERON`）。

**改进**
- **无障碍的判据换了**：以前是"设置里有没有这一项"，现在是"服务有没有真的连上来"（`ChatCaptureService.live`）。旧判据在覆盖安装 / 被系统冻结后会把"设置开着、服务死了"当成健康状态 —— 这正是每次都要手点的原因。
- **就绪卡多一态**：「无障碍权限开着，但服务没在跑」单独一态，并直接指到下面的一键修复（以前只有"已开 / 未开"两种）。
- 「设置开着但服务没在跑」时不是重写一次，而是**先写不含本服务的列表、再写回**（中间隔 600ms）—— 值不变系统不会重绑，等于什么都没做。改完还等最多 4 秒确认服务真的连上来，没连上就报失败，不假装成功。
- root 卡文案改成按「有没有写系统设置权限」讲，不再按「有没有 root」讲：真机上 `su` 对 App 是隐藏的（SUSFS），能不能修只取决于那条权限；拿不到时直接把那条一次性命令印在卡片上。
- 写无障碍那一格**只合并、不覆盖**别的无障碍服务；`settings get` 返回的字面量 `null` 会被吃掉（否则会把 `null` 当成一个服务名写进系统设置，留下永久脏数据）。

**已知限制**
- 这台机器上 App 拿不到 `su`（SUSFS 把 `/system/bin/su` 对 App uid 隐藏，exit=127），所以要先**一次性开通**写系统设置权限：KernelSU 里允许本 App 请求 root，或 `adb shell pm grant com.jev.probe android.permission.WRITE_SECURE_SETTINGS`。开通之后就不再需要 root。
- 「开机后自动修」没在真机上验过（要重启，且锁屏未解锁时系统不发 `BOOT_COMPLETED`）；覆盖安装后的广播送达不稳定（两次明确计数里一次送到、一次没送到），所以可靠的是「打开软件时自动修」。
- 省电白名单那一项在本机每次都跳过（既没 root 也没权限），`cmd deviceidle whitelist` 从 App 走通没测过。
- 单测 511（含 7 条新用例），APK 34,457,503 字节。

## 未发布 — 人设卡才是那个杠杆，知识库要「预扫成一张卡」才有用

这一版回答两个问题：「你确定知识库在回复的时候有效果吗」和「加个人设系统」。办法是真的把提示词拆成几条臂、发给同一个模型、再用另一个模型盲评打分。
完整数据见 `_reports/kb-effect_report_2runs.md`，研究清单见 `_reports/research-wenyi-yanwai_report.md`。

**结论（两轮实况 A/B，6 个网调场景，盲评 1–5 分，每臂约 10–22 次判分）**
| 臂 | 提示词长度 | 领域词 | 盲评 |
| --- | --- | --- | --- |
| 人设卡 + BM25 命中的 5 段原始片段 | ~3,440 字 | 0.92 | 4.32 |
| 人设卡，不注入任何笔记 | ~255 字 | 1.04 | 4.14 |
| **只有笔记、去掉人设卡** | ~3,261 字 | 0.42 | **3.45** |
| 人设卡 + 一张自动预扫的领域卡 | ~910 字 | 1.12 | **4.75** |

- **人设卡是最大的单一杠杆**（去掉它 −0.86 分），而原始片段几乎没有边际收益：提示词长 13 倍，只换来 +0.18。
- **整库预扫成一张领域卡最好，而且只有四分之一长**。「存 678 条笔记等着被检索」这条路本身是低效的——模型读不完、BM25 也猜不准该带哪几条。

**新增**
- **人设模板**：设置里编辑联系人人设时，上面多一排「网调·我是主」「网调·我是奴」「日常」三个按钮，点一下套用（已有内容会先问一句再覆盖）。模板写全了 `PersonaCard` 认得的键，所以套用后立即是「结构化人设」，而不是一段自由文本。
- **人设卡的「主题」字段**：`情境` 说的是此刻什么场合，`主题` 说的是这件事整体属于哪一类（例如「网调」）。结构化输出里会带一句「回复要具体到这个语境的规矩、步骤和说法，不要给脱离语境的通用安慰」。认 `主题/领域/话题/topic/domain/subject` 六种写法；写不认识的键（例如「主题方向：网调」）会退回自由文本——猜错主题比不认更坏，有测试钉住。
- **「整库预扫成领域卡（推荐）」按钮**（知识库页）：把整库按来源均衡采样（不超过 24,000 字）发给助手模型，归纳成一张不超过 900 汉字的六段式领域卡（角色与关系／称呼与语气／典型流程／常用说法／边界与安全／不要做什么），存成一条**常驻**笔记，之后每轮分析都带上它，不再靠检索去猜。同一主题重复预扫会覆盖，不会越攒越多。真机实测：678 条笔记 → 采样 12,119 字 → 440 汉字的卡，内容是「请安、跪好、报数、请示、加罚、后关怀、软界限」这类真实高频词，而不是通识。
- 三张模板的人设与领域卡的提示词都有单测；`DomainBriefTest` 11 个用例里最重要的一条是「一本 300 段的大书不能把采样额度吃光」。

**改进**
- **复查（S1）现在拿得到人设卡**。它的判据里一直写着「有没有和已知的称呼、关系冲突」「有没有越过已经明确的边界、安全词」——但它从来没拿到过这些字段，那两条标准只能退化成「读着像不像」。现在复查与起草用**同一张**卡（联系人专用人设优先，回落全局），硬边界**逐字**给它（因为安全门是逐字匹配）。不给卡时提示词逐字不变，有测试钉住。

**已知限制**
- 注进去的专属内容其实很少被复述：两轮里只有 5 次「只在注入内容里出现过的四字串」落进回复，而每个场景可用的这类串有 1,700–2,000 个。知识库改变的是**语域和词汇分布**，不是「背诵」。
- 判分样本小（每臂 10–22 次），数字当方向看，不当精确值。

- **一次分析真正进提示词的笔记从 1.4 条变成 3.6 条**，聊天历史从「一条都进不去」变成 1–3 行。原因是预算被单条笔记吃光：切段大小 1200 字 ≈ 1200 token，和 `BUDGET_TOKENS` 是同一个数量级。切段改成 **600 字**，预算 **1500 → 3000**，并新增 `MIN_HISTORY = 6`——裁剪顺序改成「历史先降到 6 行 → 再从末尾丢笔记 → 最后才动历史」，而不是先把历史全丢掉。
- 单文件切段上限 `400 → 2000`。原来的 400 是因为「存一条笔记要重写整个文件」才是二次方，而批量写早就是一次落盘了，理由不存在了。
- 导入时按正文**去掉知识库里已有的内容**，并在同一批内去重；跳过多少条如实报出来。旧库里 10 组完全重复就是这么来的。
- 真机知识库从 **140 条 / 覆盖 18 个文件 / 151,418 字** 变成 **678 条 / 25 个文件 / 390,064 字**，重复 0 组。原先完全没进来的 9 个文件里包括占语料 65% 的那本书。

**新增**
- `TextNorm`：抽取器输出的出口统一修两类**会让笔记无法被检索**的文本问题——OCR 每个汉字之间插的空格（`这 篇 教 程`，空格把中文重叠 bigram 全切断），以及 PDF 把字形映射成康熙部首（`⽹` 而不是 `网`，部首落在所有汉字区间之外，永远匹配不上）。全角标点故意不动。这样用户在手机上重新导入同一批文件不会再得到死数据。
- 重建工具链（`app/build/scratch/`，不进产品）：多格式抽取 → 按汉字占比判断抽取是否失败并重抽 → 关掉 OCR 空格 → 部首规范化 → 文档级近重复去重 → **用应用自己的切段器**生成笔记 → 推送 `files/kb/notes.json`。

**修复**
- **导入页根本没法用**：每个文件一行的解析报告是 `wrap_content` 且在唯一可滚动区域**之外**，20 个文件就把滚动区压成 0 高、自己又滚不动，两个按钮被挤出屏幕。报告移进滚动区，按钮行固定在外；并加了布局断言测试。
- **`matchNotes` 把自己刚算出来的排名丢掉了**：结果最后按 `updatedAt` 重排，于是「哪条最相关」取决于笔记什么时候写的。同一批导入的笔记时间戳全一样，所以一直看不出来。现在按 BM25 分数顺序返回。
- **短查询被虚词表误杀**：查询 `会议` 的唯一 bigram 含虚字 `会`，被整个滤掉后返回「没有匹配」。改成「查询的 bigram 少于等于 2 个时不做过滤」。
- **点桌面图标总回到「无障碍」设置页**：`startActivity(ACTION_ACCESSIBILITY_SETTINGS)` 没带 `FLAG_ACTIVITY_NEW_TASK`，系统设置页被塞进本 App 的 task 并成为 root（MainActivity 已 finish），于是 `am start` 永远只回答「已投递给当前顶层实例」。三个系统设置页统一改走带 `NEW_TASK` 的入口。

**已知限制**
- 一份占全库一半以上的文档仍然可能同时占满 5 个命中位（实测某一轮 5/5 全来自同一本书）。配额能缓解，但会把弱相关的笔记拉进来填空位，没有实测证据前没改。
- `minScore = 0.15` 基本不起作用：实测最高分 2.7–6.5、过线 2–99 条，真正的上限一直是 top-5。要修得用相对最高分的比例。
- 应用侧 OCR 仍受「最多 20 页」限制。

## 未发布 — S3：L1 注入源跑通（v2.0 第三步，试点 Telegram）

对应 `docs/lsposed-enhancement-plan.md` 的 S3。这一版**开始读真实消息对象**了：在装了框架并把某个 App 打开的机器上，模块直接从宿主聊天页读出成段正文、发送者、时间与消息 id，推回本 App；取不到就一秒内安静落回无障碍。默认仍然全关。

**新增**
- **L1 注入源（试点 Telegram）**：不再从宿主 Activity 反推当前页面，而是直接钩住 `org.telegram.ui.ChatActivity` 的生命周期，拿到那个聊天页对象本身，读它的 `chatAdapter` / `messages`。这样一来宿主内部页面拓扑怎么变都不影响——上一版靠 `actionBarLayout.getFragmentStack()` 反推，在 12.10.1 上时对时不对。
- 真机实测同一台机器、同一个会话：**无障碍读到 0 条，注入层读到 26 条**（`titleLen=4`，payload 2880 字符，`accepted=true`）。这是「LSPosed 是增强」这句话的量化依据：不是更快，是从 0 到 26。

**改进**
- 注入快照仍然有界：只取最后 60 条里的一部分，再由 `InjectTimeline` 按 **最多 40 条 / 总共 6000 字**（正文长度之和）双预算从最新往回裁，整数条、不截半条。日志里 `tg push … msgs=60` 报的是**读窗口**条数，App 侧 `snapshot=msgs=26` 是**裁完**的条数，两个数口径不同。
- 聊天页判定改成「以钩到的对象为准」，窗口里的 View 只作加强证据。原因是退出聊天页后聊天页的 View 会作为**缓存视图**留在窗口里，老判据会把上一个会话的适配器当成当前会话。
- L0/L1 对拍多了**重叠数**（`cmp … overlap=3`）：两侧按「分边 + 正文」配对的多重集合交集。原来的位置对齐回答的是「新的那一头从第几条开始对不上」，可两层窗口长度不同时最新几条 L0 根本没有，`aligned=0`，就只剩「对不上」一个结论；重叠数与位置无关，才说得清「两层读的是同一段聊天，L1 多出两条」。仍然只输出计数，不含正文。

**修复**
- `XposedBridge.hookAllMethods` 只挂**本类声明**的方法：子类没覆写 `onResume` 时它一个都不挂，**而且不报错**（第一版就是这样「成功」地什么都没挂上）。改为沿继承链逐层挂钩并**记下真正挂上的个数**（真机 `methods=6`）——「挂零个」和「挂上了但读不到」必须是两行不同的日志。
- 补上桥的冷启动盲区：刚覆盖安装后目标 App 处于 stopped 状态，`setPackage` 点名广播默认进不去，模块于是按 fail-closed 一个钩子都不装、表现成「开关明明开着却什么都没发生」。广播补 `FLAG_INCLUDE_STOPPED_PACKAGES` 后正常。
- `methodOf()` 反射取到方法后补 `isAccessible = true`：宿主的适配器是**非 public 的嵌套类**，直接 `invoke` 抛 `IllegalAccessException`，被 `runCatching` 吞掉后跟「方法不存在」长得一样。
- **退出聊天页时主动撤回快照**。原来退出后模块什么都不推，账本里上一条会一直留着：从会话 A 退出来点进 B，App 若先抓到 A 的快照，分析的就是**另一个会话的内容**（B 读不到时更是一直错下去）。账面有 120 秒 TTL 兜底，但那意味着最多错两分钟。现在退出即推一条**空快照**撤回，App 侧把「空」判成「没有数据」落回 L0——**不能**把空快照当有效数据，否则 `injected ?: adapter.extract(...)` 会把无障碍那一份也挡掉。真机：模块 `tg retract 退出聊天页，已撤回上一条快照`，App 侧 12 秒内连续 14 次 `inject … skip=empty`。

**已知限制**
- 只做了 Telegram。方案 S3 原指的宿主是微信，微信的 L1 直读**尚未开始**（`HookTargets.SCOPED` 里目前只有 `org.telegram.messenger`）。
- 方案原定的验收是「L0 vs L1 **逐条**对拍」，目前只做到「能比、能比出差异」：位置对齐 + 分边/正文差异 + 位置无关的重叠数都有了，但**错位时怎么算还没定义**（真机上两层窗口长度不同、L0 常为 0，`aligned=0`）。另外 Telegram 上 L0 读到的就是 0 条，所以真机那条 `overlap=0` 是「没得比」，不是「比出来一样」——重叠数这条规则目前只有单测覆盖，真机没有能同时被两层读到的宿主的样本。
- 不带框架的机器上，Telegram 本来就读不到（无障碍拿不到它的消息树），这一版没有改变这一点——它只是让装了框架的人读得到。
- 详细报告与全部真机输出：`_reports/s3-telegram-l1_report.md`。

对应 `docs/lsposed-enhancement-plan.md` 的 S2。**这一版不读任何消息**：只把地基铺好——模块能在目标 App 的进程里以本 App 的身份活起来、按 App 单独开关、连接状态看得见、读不到时一秒内安静退回无障碍。默认全关，不开就是今天这个纯无障碍助手，功能一模一样。

**新增**

**改进**
- 采集链路变成有阶梯的：注入源（S3 起才有数据）→ 无障碍适配器 / 截屏 OCR，谁拿到算谁。来源写进快照（`inject` / `a11y` / `ocr`），诊断日志里连降级原因一起留着（`inject … skip=no_data`），不静默。
- 跨进程桥的通道顺序：显式广播 → 兜底 Provider / 绑定 Service。需要答复的调用走有序广播、4 秒硬超时，拿不到答复就回落，绝不拖住宿主启动；心跳与快照是单向的，发不出去就算了。桥收到的每一条都要过 UID 门禁（只认本 App 自己与已开启的 App），迟到的心跳/快照不能覆盖新状态。

**修复**
- 真机定位到的两个坑，记下来省得下次再踩：①Android 14 起广播默认不带发送方身份，不显式声明 `setShareIdentityEnabled(true)` 时接收端只拿到 `INVALID_UID`，表现是「模块这边显示发出去了、本 App 那边一直拒收」，注入层静默失效；②模块侧报的版本号改成编译期常量 `BuildConfig.VERSION_NAME`，之前查宿主 Context 报出来的是**宿主 App** 的版本号。

- 强停本 App 之后广播**不会**唤醒它（系统的 stopped-package 语义），设置页会显示「未连接」——用户显式强停就等于桥断开，这是有意保留的语义。

## 未发布 — S1：会话台账 + 证据复查（v2.0 第一步）

对应 `docs/lsposed-enhancement-plan.md` 的 S1：先不碰注入层，只用现有的无障碍 + 历史做「长上下文质量工程」。要解决的是评测里反复出现的两个症状——早期说好的称呼、边界和没做完的事会随着历史滚出注入窗口而丢；以及排序选出来的首选候选仍然接不住对方。

**新增**
- **会话台账**（默认开，随「记录聊天历史」一起生效）：把整段聊天历史预扫成一张卡片——称呼、关系、语气基线、在办的事、已经明确的边界、固定说法——然后用**增量**方式维护（旧台账 + 上次整理之后的新增 → 新版台账），注入在原始历史**之前**，并要求「回复必须与它一致，台账里没有的事不要编」。这样称呼和在办的事不会因为滚出 20 条窗口而消失。三道闸门保证它不会把这一轮带崩：关掉就整个不做；`coveredUntil` 没过期就不重建（否则每来一条消息就多一次模型调用）；重建失败或解析失败**永远**保留上一版。台账只进回复提示词，不进判断那一路。
- **证据复查**（默认关，多一次模型调用）：排序之后把三条候选连同台账和判断结果一起交给复查模型，逐条核验五件事——有没有直接回应对方最近这条、有没有贴住真实氛围与亲密程度、有没有和已知称呼/关系/固定说法冲突、有没有编造对话里没有的事实人计划承诺、有没有越过已明确的边界/禁区/安全词。站不住的那几条会被重写（把「上一条被判定为：<理由>」加进避免清单再重新起草），其余两条原样不动。设置里有独立的「复查接口」三项，留空就沿用回复接口。
- 设置 → 知识库新增两枚开关和复查接口地址/模型/密钥（密钥留空沿用回复密钥）。

**改进**
- 复查是**失败即放行**：判定为 false 但没给理由的候选会被保留（理由为空就说明它没说清哪里出问题，这种时候宁可留下候选也不猜）；接口报错、返回不是 JSON、条数对不上一律保持排序结果不动，只写一行 Trace（`review keep all` / `review reject <序号> ` / `review failed`）。
- 台账和复查的提示词同样只有一份、在 Kotlin 里（`LedgerPrompt` / `ReplyReview`），评测脚本通过 Gradle 导出真实提示词，不可能和 app 漂移。
- 顺带修了历史摘要那一路的转写：读不出归属的消息行原来被默认为「对方」，现在和提示词里的规则一致写成「发言人不明」。

**已知限制**
- **实况 A/B 没跑**：本机没有 `JEV_REPLY_KEY` / `DEEPSEEK_API_KEY` / `OPENROUTER_API_KEY`，`--ledger` 的两臂对比只有离线层证据（台账提示词导出、台账注入进提示词的逐字断言），没有「有台账 vs 无台账」的实况分数。跑法：`python3 tools/jev/eval_roleplay.py --out app/build/rp_base.json` 与 `python3 tools/jev/eval_roleplay.py --ledger --out app/build/rp_ledger.json`，两条命令唯一的差别就是 `--ledger`；台账两份臂共用一份缓存（`app/build/ledgers.json`），否则「台账本身写得更好」会被算成台账的功劳。
- 台账每重建一次多一次模型调用，复查每次分析多一次；两枚开关都能单独关掉，复查默认关。
- 台账是模型整理的，可能整理错。所以它只被当作「背景」注入，末尾仍写着「边界只多不少：这里的边界是补充，取消不了上面的硬性禁止」——台账写的边界能补充硬禁，但取消不了任何一条。同一称呼出现两种说法时会写一行 Trace 而不是静默混进提示词。

## v1.0 — 2026-09-21

**新增**
- 首个可用版本：跑通全链路——读聊天气泡 → 用 Jev 判断模型给出真实意图、危险等级（1–9）、对方要什么、该不该马上回、最佳动作（约 1 秒出结果）→ 生成模型（DeepSeek）起草 3 条候选回复 → Jev 给候选排序 → 半透明悬浮窗展示 → 一键填入输入框。
